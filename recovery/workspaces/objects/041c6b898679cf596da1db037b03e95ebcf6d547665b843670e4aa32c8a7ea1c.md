## 1. Total move coverage semantics (all `Inc(P)`, no heuristic dominance)

**Code (`scripts/total_coverage_bb.py`):** `incomparable_pairs(succ,n)` returns all `(i,j), i<j` with neither `i<j` nor `j<i` in the TC state. For each explored non-terminal, nonzero-budget node, the solver loops over **every** element of `inc` and appends a `move_record` for each move (`move_records.append(...)` on each iteration; no `break` on finding a sorter/refuter move). `[definition/deduction, code read]`

**Game semantics used:**
- `sorter_win` move iff **both** adversary answers (`lt` = add `i<j`, `gt` = add `j<i`) lead to `SORTER_WIN`.
- `refuter_win` move iff **at least one** answer leads to `REFUTER_WIN`.
- Node `SORTER_WIN` if any move is `sorter_win`; else `REFUTER_WIN` if `not any_unknown`; else `UNKNOWN`.

This is the exact minimax value propagation for `G(n,k)` and matches the doc’s stated semantics. The recognition of `any_sorter_win_move` is an exact early recognition of node value, **not** a heuristic dominance/pruning of move choices or adversary answers; the implementation continues enumerating remaining moves for coverage. No branch-order heuristic dominance is used to discard moves or answers without proof. Memoization uses exact identity keys `(succ_tuple, budget)`, with an explicit note that poset congruence/canonicalization is not used for certified claims. **Pass, with the caveat above.**

## 2. Budget/TC/answer checking

**TC/extend:** `extend(succ,i,j)` copies masks and propagates `new_g = succ[j] | (1<<j)` to `i` and every `x` with `succ[x]` containing `i`. This is the same TC extension pattern as `scripts/budgeted_dfs.py:extend` and preserves transitive closure when starting from a closed state. `[deduction, code comparison]`

**Terminal/budget:** `is_total => SORTER_WIN`; `b==0` and not total => `REFUTER_WIN` with incomparable count recorded. Recursive answers use `b-1`. **Correct for `G(n,k)` height/budget convention.**

**Caps/stats:** `tick` enforces `node_cap` and `time_cap`; on cap returns `UNKNOWN`, records `cap_reason`/`first_cap_path`. Node count reaches `cap+1` in capped runs (e.g. 50,001 / 120,001), consistent with traces. `answer_checks` counts recursive answer evaluations attempted (subject to cap checks). **Adequate for a capped fragment; not an independent proof checker.**
