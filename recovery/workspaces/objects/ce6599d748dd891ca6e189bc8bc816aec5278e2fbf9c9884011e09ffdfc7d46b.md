## 2. Path (i) assessment — not discharged

**Requirement (as stated):** explicit simultaneous PFP over interpreted config+cell relations.

**Finding:** The artifact does not give an explicit simultaneous PFP system whose components are interpreted as ATM/config/cell relations in the complete normal form of an FO(PFP) capture construction. It gives:

- an informal/configuration decomposition `Pos, Time, Mode, Pair` (§3);
- a schematic acceptance operator `ψ_accept(AC; Pos,Time,Mode,Pair)` (§6);
- a conditional PFP form `Φ_game := ∃Pos,Time,Mode,Pair (Init(...) ∧ [PFP_{AC,...} ψ_accept(...)](...))` under a standard encoding.

This is **not** an explicit simultaneous PFP over cell relations (tape cells, head/state/time indices) with all components and their FO update rules spelled out. The text acknowledges the gap by deferring to “a standard encoding…” and by listing the global simulation/normal-form instantiation as residual (§7). Therefore path (i) is **not concretely discharged**.

The artifact’s treatment of the old fixed-tuple decoding blocker is reasonable as motivation `[deduction]`: representing arbitrary `Pos` content by a fixed `d̄∈W^r` cannot range over `2^{Θ(n^2)}` posets when `|W|=N`, whereas a binary relation `Pos(u,v)` can. This explains why the note moves away from naive path-(i)-style tuple decoding, but it does not itself complete path (i).

## 3. Path (iii) assessment — local ingredients concrete; global closure not discharged

### 3.1 Explicit ATM/config encoding — **partially concrete**

Concrete elements:
- `M_G` is described as an alternating computation for `G(n,k)` with existential `MS` (sorter), universal `MA` (adversary), and sinks `MAcc/MRej` (§5).
- Configuration components `Pos/Time/Mode/Pair` and domain restrictions are stated (§3).
- Space claim `O(n^2)+O(log k)+O(1)=O(N^2)` and representability by fixed-arity relations is plausible `[deduction]`.

Limitations:
- `M_G` is not a fully formal ATM tuple `(Q,Σ,Γ,δ,q0,...)`; it is a game/ATM description. That is acceptable as a research encoding attempt, but the remaining FO(PFP) simulation requires a precise configuration graph/machine normal form.
- `Mode` uses 3 bits with order-min tags; `Pair` is a selected pair relation. These are concrete enough for the local formulas, but the global PFP proof must encode all needed control/configuration state in the chosen fixed-point framework.

### 3.2 Fixed FO formulas — **mostly concrete, with caveats**

The artifact gives fixed FO formulas over `A(w)=(W,<,One,Hash)` for:
- well-formedness/parameters `HashPos, Key, Ctr, Zero, MaxK, SuccCtr, HasBudget`;
- state decoding/helpers `PValid, Incomparable, Total, ExactlyOneTime, NullPair, HasPair`;
- mode tags `IsMin, NotMin, MS, MA, MAcc, MRej, ExactlyOneMode`;
- initial/accepting forms and transitions `Init, Acc, StepPos, YieldE, YieldA0, YieldA1`.

Caveats:
- `HashPos` is defined as `Hash(h) ∧ ∀z(Hash(z)->z=h)`, which is appropriate if `Hash` is intended as a unary marker that might not be preconstrained to a singleton by the structure definition alone; `WellFormed_w` then enforces singleton hash. The structure is declared as `Hash={n+1}`, so this is consistent but slightly redundant.
- `Ctr(t):=∃h(HashPos(h) ∧ (t=h ∨ h < t))` makes `Zero` (`Hash`) serve as comparison count 0. This is a concrete encoding choice; it is workable because `Zero` is tested and `SuccCtr` moves along `Ctr` elements in order. It should be checked that no formula conflates key position `n+1` with an actual key — keys are restricted to `Key(x):=x<h`. OK.
- `ExactlyOneMode` is described textually (“with pairwise exclusion by table”) rather than written as a full formula. Minor gap.
- `Init` gives two forms (§4, lines 112–126 in the artifact); the second is the clearer general form. A completion should fix one canonical definition.
- Some helper predicates (`ExactlyOneTime`, `HasPair`, `PValid`) are defined but not explicitly conjoined into every transition’s invariant; `YieldE/A0/A1` assume/use intended structure. A full proof should show reachability preserves them.

### 3.3 Legal `G(n,k)` transitions, TC, budget `<=k` — **largely concrete**

Strengths:
- `G(n,k)` is aligned with project docs: sorter picks incomparable pair, adversary answers `x<y` or `y<x`, state becomes transitive closure, budget decreases/steps once per comparison (`S(n)<=k` iff sorter wins) — consistent with `docs/research-certificates-barriers.md` §0/Claim A.
- `YieldE` requires non-total state, `HasBudget(t)`, selects `Incomparable(Pos,a,b)`, stores the pair, keeps `Pos/Time` unchanged, and moves to adversary mode. This matches the sorter’s legal move.
- `YieldA0/A1` cover both answers, apply incremental TC via `StepPos`, advance time by `SuccCtr`, clear the pair, and branch to accept/continue/reject based on totality and remaining budget. This matches adversary outcomes.
- `StepPos(Pos,x,y;u,v) := Pos(u,v) ∨ ((u=x ∨ Pos(u,x)) ∧ (y=v ∨ Pos(y,v)))` is the standard FO incremental TC update **under the stated precondition** that `Pos` is a transitively closed strict partial order and `(x,y)` is incomparable. The artifact states this precondition `[deduction]`; a full discharge must prove preservation/closure.
- Budget `<=k`: `HasBudget` gates `YieldE`; `SuccCtr` enforces a single increment; acceptance is allowed on `Total(Pos')` (including exactly at `k` by construction), and non-total + `MaxK` leads to reject. This addresses the requested `budget<=k` condition.

Caveats/falsification targets (some already noted by the artifact):
- `Total(Pos)` on the antichain is true only for `n<=1`; `Init` handles this explicitly. Good.
- The selected pair must be incomparable in the pre-adversary state; `YieldE` enforces `Incomparable(Pos,a,b)`, and `YieldA0/A1` also require `Incomparable(Pos,a,b)` on current `Pos` with the stored pair. Since `YieldE` does not change `Pos`, this is consistent, but a proof should make the invariant explicit.
- `PValid` preservation after `StepPos` is asserted, not proved.
- `SuccCtr`/`MaxK` behavior at boundary elements depends on `Ctr` containing `Zero=Hash`; this is coherent but nonstandard and should be checked carefully in a formalization.

### 3.4 AC-independent decoding — **substantially supported, with formalization caveat**

The local decoding/transition formulas `PValid, Incomparable, Total, Init, Acc, StepPos, YieldE, YieldA0, YieldA1` and parameter helpers do not mention `AC`. `ψ_accept` uses `AC` only positively as the acceptance relation on successor configurations. This satisfies the intended **AC-independence/positivity** requirement at the schematic level.

Caveat: the final `Φ_game` writes `∃Pos,Time,Mode,Pair (...) ∧ [PFP_{AC,...} ψ_accept(AC,...)](Pos,Time,Mode,Pair)` in an informal notation. In standard FO(PFP)/IFP, the fixed-point variable is a relation of fixed arity over the domain, and simultaneous/mutual or tuple-encoded configurations must be represented according to the logic’s syntax. The artifact correctly labels this as conditional on a standard encoding; therefore AC-independence is not enough to claim a complete discharged formula.

### 3.5 PFP/IFP acceptance equivalent to `S(n)<=k` — **not discharged**

The artifact states the right target:
- `M_G` accepts iff sorter wins `G(n,k)` iff `S(n)<=k` on well-formed inputs `[deduction]`;
- `ψ_accept` is a positive acceptance operator;
- an LFP/IFP/finite-stage acceptance form is plausible on reachable game states;
- a PFP/FO(PFP) global sentence is the intended closure object, conditional on simulation instantiation.

However, **equivalence as a concrete discharged result** would require:
1. a complete, syntactically valid FO(PFP) (or IFP, as used in the chosen capture theorem) formula/sentence over `A(w)`; and
2. a proof that its semantics on `A(w)` equals `S(n)<=k`.

Neither is fully provided. The artifact explicitly says “Not a fully discharged formula-level FO(PFP) proof from scratch” and identifies the missing simulation lemma/proof (§0, §7). That blocker statement is precise and is the main reason the note does not overclaim closure.

## 4. Overclaims / smaller-class claims

**No smaller complexity-class overclaim found.** The artifact explicitly disclaims:
- `P`, FO(LFP) on the bare word, NP/coNP membership from positivity/stratification (§0, §6.225).
- any improvement beyond the established PSPACE/FO(PFP)-in-principle context.

**Borderline phrasing to keep guarded:**
- “Path (iii) is made concrete at the ATM/transition/encoding layer, modulo…” is acceptable if read with the immediate qualifier; without the qualifier it could be misread as discharge. The verdict section does include the qualifier.
- “Therefore `M_G` accepts ... iff `S(n)<=k`” (§5.191) is a reasonable local equivalence claim given the game definition, but in a closure audit it should remain conditional on the exact correspondence between `M_G`’s formalized transitions and the project’s `S(n)`/`G(n,k)` model. The artifact later frames global closure as conditional, which mitigates this.
- The LFP/IFP remark (§6.219–223) is plausible for the finite alternating game but should not be promoted to a class-membership claim for `SORT-BOUND-U` on the input word; the artifact correctly avoids that promotion.

No evidence of `sorry`/axiom abuse is relevant (not a Lean artifact).
