## Minor observations (non-blocking)

1. **Line-index schema:** `pymupdf-lines.json` uses `{page,width,height,lines:[{text,bbox}]}` with page lines implicitly enumerable by order; `target-extract.json` uses `line_in_block`. The markdown tables present page-dump-style indices (e.g. 013–036). This is clear enough in context but could be made mechanically explicit by stating “1-based index in `pymupdf-lines.json.pages[page-1].lines`”.
2. **Target-extract coverage vs. markdown coverage:** Theorem 2 in `target-extract.json` includes only the initial statement block, whereas the markdown table also includes schedule/proof-clue lines from the same page dump. This is acceptable because the markdown cites `pymupdf-lines.json`/coordinates and does not claim all table rows come only from `target-extract.json`; it is a small documentation asymmetry.
3. **Math reconstruction boundary:** The artifact appropriately avoids reconstructing fragmented equations into TeX-level claims except as clearly labeled fragments. Any downstream use must treat (18), (44), Thm 2 `ϕ`, and Thm 3 display/recurrence as requiring rendered-page semantic transcription before certification.

The extraction/doc is **acceptable as the smallest public extraction step** for TR20-096 targets requested, with the obstacles it states (missing `pdftotext`/`mutool`, curl TLS-56 on fresh download in that session, fragmented display math, absent Corollary 3 label, and un-discharged B3/B5/B6 mathematics).
