# Pull request #49: Keep Lean verification for theorem changes; skip it for research-note-only PRs

Upstream: https://github.com/ottojung/soringp1/pull/49

The SoringP1 research program intentionally forbids low-ROI Lean formalization, yet `.github/workflows/ci.yml` currently installs Lean/Mathlib and replays the entire kernel for **every docs-only research note**. PR #44 has already triggered several redundant 90-minute-capable Lean runs despite changing no Lean source.

This workflow-only change introduces a conservative **theorem-affecting-path gate** in the existing `lean` job, while keeping the lightweight Python `reference-evaluator` job unconditional:

- Run Lean whenever `SoringP1/`, `SoringP1.lean`, `lakefile.lean`, `lakefile.toml`, `lake-manifest.json`, `lean-toolchain`, or this workflow changes.
- Always run Lean on `workflow_dispatch`.
- For PRs compare against the actual base SHA; for pushes compare against the previous commit SHA, fetching the base at shallow depth. Missing/invalid/unfetchable SHA or failed diff **defaults to full Lean verification**, never silently skips it.
- Only for changes strictly outside Lean-relevant paths, complete the existing job successfully without installing Lean or downloading Mathlib; Python evaluator still runs in its normal job.
- On this workflow-changing PR itself, full Lean build *must* execute, validating that the guard cannot disable verification of its own implementation.

No Lean proofs are added, changed, or weakened. This is a targeted efficiency fix, not suppression of required kernel checking for actual Lean changes. Review the path regular expression and the PR merge-commit vs push-base selection carefully.
